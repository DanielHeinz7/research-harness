title: The Bash guard reads the substitutions inside an unquoted heredoc body
bump: patch
plugins:
  - research-harness

SQ-29 finding F6: the lexer skipped a heredoc body wholesale, so a command
substitution written inside it was never judged and ran unseen. That is right
for a quoted delimiter (`<<'EOF'`, `<<"EOF"`, `<<\EOF`), where bash leaves the
body literal, and wrong for an unquoted one, where bash expands `$(...)` and
backticks in the body before the command runs.

The guard now scans the body of an unquoted heredoc for those two substitution
forms and lexes each as a nested command, the way a substitution in a word is
lexed, so `cat <<EOF … $(rm research/canvas.md) … EOF` is denied. The rest of the
body stays data: plain text on a line of its own reaches the command's stdin and
is not read as a command line. A quoted delimiter keeps the body unread, as
before. A body the scan cannot finish — an unclosed `$(`, or nesting past
MAX_SUBSTITUTION_DEPTH — is opaque: the redirect carries it and the verdict
judges it on the names it still spells out, which is the rule an opaque word
already follows.

`verification/SQ-29/lex.txt` L1 and L3 flip to DENY; L2, the quoted-delimiter
control, and every other row are unchanged. `plugins/research-harness/test/guard-promotion.test.js`
gains the unquoted/quoted heredoc pair, the read-only substitutions that must not
be refused, and the opaque-body case.
