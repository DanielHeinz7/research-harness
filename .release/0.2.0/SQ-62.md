Three new probes (`verification/SQ-29/probe-review.js`) found one real gap and
confirmed one deliberate over-denial is not a security hole:

- `bun`, `deno` and `php` can read a heredoc body as their program the same
  way `node`/`python3`/`perl`/`ruby` do, but neither is in
  `STDIN_PROGRAM_INTERPRETERS`/`STDIN_PROGRAM_SHELLS`, so a quoted-delimiter
  heredoc body fed to any of them is never inspected at all — not even by the
  crude substring safety net that already covers the interpreters SQ-67/69/70
  do recognise. Reproduced (R3a-R3c, verdict-only: none of the three binaries
  is installed on this host) against a body that literally names
  `research/canvas.md`; the identical body fed to `node` (R3d) is correctly
  denied. Filed as a follow-up finding, not fixed here.
- SQ-71's `statePresent` gating makes `for d in */; do echo "$d"; done` DENY
  inside a project that holds state, because the glob component-matches the
  state directory name and `for` is not a read-only verb, even though `$d` is
  never used as a path (R2a). This is a false deny, not a false allow: it is
  strictly more restrictive than intended, not a hole. No ticket filed.
