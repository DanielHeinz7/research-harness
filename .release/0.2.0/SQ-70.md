ref: SQ-70
title: An inline-program letter belongs to the interpreter that spells it, and an interactive flag keeps the heredoc body as code
bump: patch
plugins:
  - research-harness
---

SQ-69 widened the inline-program spellings for every interpreter at once, and the
letters are not shared. A heredoc body fed to three of those forms was read as
stdin data and ran:

    python3 -E <<'EOF'                -E ignores PYTHON* env vars; it carries no program
    import os; os.remove('research/canvas.md')
    EOF

    python3 -Es <<'EOF'               the same, in a cluster
    ruby -E UTF-8 <<'EOF'             ruby's -E takes an encoding, not a program
    File.delete('research/canvas.md')
    EOF

    node -c <<'EOF'                   node's -c is --check: it compiles, it runs nothing
    require('fs').rmSync('research/canvas.md')
    EOF

Only perl carries a program on `-E` (`perl -E 'say 1'` really does run the `say 1`
program), and `INLINE_PROGRAM_FLAGS`, `INTERPRETER_ATTACHED_PROGRAM_RE =
/^-[ceE]/` and `INTERPRETER_PROGRAM_BUNDLE_RE` asked all six interpreters to share
one letter set, so `-E` counted as a program for python, node and ruby too.

The three shared definitions are gone. `INTERPRETER_INLINE_PROGRAM_RE` is one row
per interpreter, and a flag outside a row leaves the heredoc body judged as the
program it may be, which is the fail-closed answer SQ-69 settled on:

    python, python3  /^-[bBdEhiIOPqSsuvVx]*c/   -c bare, attached (-cPROG, -cE) or
                                               closing a cluster of boolean letters (-Ic)
    perl             /^-[nplc]*[eE]/            -e and -E, bare, attached or bundling
                                               (-ne, -lne, -ce)
    ruby             /^-[nplc]*e/               -e alone
    node, nodejs     -e, -p, -pe, --eval, --print

The rows are not documentation guesses. python3 3.14.7 and node v24.16.0 were read
off `--help` on this machine; perl 5.40.2 and ruby 2.6.10 have no flag list in
dispute that a help text could settle, so each of their cluster forms was settled
by feeding the same body to the binary with and without the flag and seeing which
one it ran (the probes are in this ticket's verification directory:
`verification/SQ-70/probe-interpreter-flags.js`, `…2.js`, `…3.js`). Three letters
were wrong to assume:

- python's `-W`, `-X` and `-m` take a value, and that value swallows a `c` that
  follows it. `python3 -Wc` is a warning filter, and `python3 -Wc <<EOF` reads its
  program from stdin — so the boolean letters are listed one by one and no others
  are bundleable. `python3 -Xc` behaves the same way.
- perl's `-i` takes a backup suffix. `perl -ie 'print 1'` runs `print 1` as a
  script file name, not as a program, so `i` is not bundleable either.
- ruby's `-E` takes the encoding (`ruby -EUTF-8` as well as `-E UTF-8`), which is
  the reported hole; ruby's `-c` compiles and `ruby -ce PROG` compiles PROG, so `c`
  bundles where python's does not.

Where a program letter is not last, the probe decided it rather than the pattern:
`perl -en PROG` and `ruby -en PROG` run the program `n`, so the body is data and
they stay allowed; `perl -ie PROG` runs `PROG` as a file, so it does not. Two
spellings that SQ-69 denied are now allowed because the binaries accept them:
`perl -lne PROG` and `python3 -Ic PROG`. The shells are untouched: the `-c` family
is still `SHELL_COMMAND_FLAG_RE`.

`test/guard-promotion.test.js` gains the SQ-70 case: ten DENY rows (the three
reported forms, ruby's attached `-EUTF-8`, SQ-69's `-W`, and the four flags that
are not programs for anyone — `node -c`, `ruby -w`, `python3 -Wc`, `python3 -Xc`,
`perl -ie`) and fourteen ALLOW rows (perl's `-E`/`-e`/`-ne`/`-lne`/`-ce`, python's
`-c`/`-c'…'`/`-Ic`, node's `-pe`/`--eval`/`--print`, ruby's `-ne`/`-e`, and one
shell cluster). Reverting the hook fails the case with an `AssertionError` on
`python3 -E`, and replaying every row through the reverted hook shows the damage
directly: 5 of the 10 DENY rows come back as ALLOW and 2 of the 14 ALLOW rows as
DENY. `probe-baseline.js` moves no row (its transcript is byte-identical to the
one HEAD's own hook produces) and `probe-lex.js` is identical to
`verification/SQ-29/lex-after-SQ-60.txt`.

An inline program is not the whole story, though. Python's `i` in a boolean cluster
and node's `-i`/`--interactive` make the interpreter read standard input as code
once the inline program has run, so an inline flag beside them leaves the body a
program after all. Feeding the same body to the binaries settled every form: the
body ran under `python3 -i -c 'pass'`, `python3 -ic 'pass'`, `python3 -Ii -c 'pass'`,
`python3 -uic 'pass'`, `python3 -Ei`, `python3 -iE`, `python3 -i`, `node -i -e 1`,
`node -e 1 -i`, `node --interactive -e 1` and `node -p 1 -i`; it did not run under
`perl -e PROG -i`, `perl -i -e PROG`, `ruby -i -e PROG` or `ruby -ni -e PROG`,
because perl's and ruby's `-i` is in-place editing and never reads stdin as code.
`INTERPRETER_INTERACTIVE_PROGRAM_RE` therefore has a row for python (the `i` of the
boolean cluster) and for node (`-i`, `--interactive`), and an interactive flag wins
over an inline one. The letter may only be a cluster letter, never the character
before a closing `c`: `python3 -ci` attaches `i` as `-c`'s program and runs it.

The other order follows the binary rather than the pattern, and the two
interpreters differ. Python takes the program out of `-c`'s next word and stops
reading options there, so `python3 -c PROG -i` hands `-i` to the program as an
argument and the heredoc body stays data; `INTERPRETER_PROGRAM_ENDS_OPTIONS` keeps
that spelling allowed. Node and perl keep reading options, so `node -e 1 -i` does
enter the interpreter. The case grows eleven DENY rows (the interactive forms
above) and five ALLOW rows (`python3 -c 'pass' -i` and the four perl/ruby `-i`
spellings).
