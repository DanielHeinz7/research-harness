---
ref: SQ-71
title: A command cannot touch research state that is not there, so the read-only rule does not engage for a project with none
bump: patch
plugins:
  - research-harness
---

The guard decides whether the project-state read-only rule applies by asking
whether a command *could* reach the state, and it answered that question by
speculation rather than by looking. A word the guard could not read — an operand
carrying a substitution it never resolved, a pattern whose expansion it could not
compute, a `cd` it could not follow — counted as touching the state whether or not
the project held any. A glob onto the state directory counted the same way even
when the directory was not there. So in a checkout with no `research/` at all,
ordinary shell lines were denied, each with a reason that named a state the
project did not have:

    for d in */; do echo "$d"; done                    `for` is not a read-only command
    while true; do l=$(sysctl -n vm.loadavg); … done   `while` is not a read-only command
    x=$(cat a); rm "$x"                                `rm` is not a read-only command

The read-only rule now reads the state it is about. `bashVerdict` asks whether the
state directory holds the canvas or the decision log — the two files that *are* the
state — and only then lets an unreadable word, an unresolvable operand, an
unfollowable `cd` or an uncomputable pattern count as a touch. Where there is no
state, those words are speculation about a location that does not exist, and the
rule has nothing to refuse; the words that spell the state's location are still
judged, exactly as SQ-65 already had them, so this is a narrowing of the
speculative triggers and not of the literal ones.

Why the same reasoning does not hold inside a stateful project for a word that
names nothing under the state dir (`for d in */` where `research` is present):
there the glob does land on the state, the rule is about state that exists, and
the touch is not speculation. That over-denial is real and is filed against SQ-62
rather than widened here.

The state is defined as the two files, so a directory that holds neither —
`mkdir research` on its own — is no state either, and the rule does not engage.
The bare name and the glob are let go there (`rm -rf research`,
`rm -rf resea[r]ch`); a path that spells the location is still denied, because
that is the word that would create the state SQ-65 keeps watching.

What the narrowing must not touch, and does not: the harness state directory
(`~/.claude/research-harness`, or `RESEARCH_HARNESS_STATE_DIR`) admits no form in
any project (SQ-27); accepting a statement and setting the CLI's own environment
on the command line are refused because they name the act, not the state; and
`git checkout HEAD -- research/` and `cat > research/canvas.md` stay denied in a
bare project, since they spell the location they would create.

One boundary is deliberately left where it stands: the state is read once, where
the command stands, so a single line that creates the state and removes it in the
same breath (`research-harness init && rm -rf */`) is judged as the project was on
entry and is allowed. Judging a line's own effect on its later words is a
different problem from this one.

`plugins/research-harness/test/guard-promotion.test.js` gains the SQ-71 case, in
three tests: the bare project (the three rows above and four more speculative
forms, now ALLOW; `research-harness init` and `mkdir -p research` still allowed;
the spelled-path, harness-state and `accept` rows still denied, both the bare CLI
word and `node … accept`), the empty state directory that is no state, and the
control — the same rows still deny in a project that holds the canvas and the
decision log. Reverting the hook fails two of the three: the ALLOW rows come back
as denials.

SQ-72 is folded in as the same defect seen from a repo that never had a
`research/`: `docker stop x`, a `for` loop and a build line with output
redirects, and the same three after a `cd "$HOME/x"` the guard cannot follow —
which is the trigger, since `base` goes null and every word after it counted as
touching. All seven are ALLOW rows in the stateless test, and `cd "$HOME/x" &&
docker stop x` is a DENY row in the stateful control, where the words after the
`cd` really can land on the state.
