title: Variant canvases, a human-only `choose`, and the guard over every canvas in the state directory
bump: minor
plugins:
  - research-harness
---

A project can now hold several framings side by side. `research-harness init
--variant <name> --lens <text>` creates `research/variants/<name>/` with its own
`canvas.md` (frontmatter `variant` and `lens`) and its own `decisions.md`, sealed
with the project's key but chained on its own, so appends to a variant never race
the main log. `status`, `review` and `log` take `--variant <name>`; `accept`
refuses it and works on the main canvas only.

`research-harness choose <name> --why <text> [--rejected <text>]` is the
researcher's pick of one framing. It refuses once the main canvas holds an
`[accepted]` statement, copies the variant's statements into
`research/canvas.md` under the main frontmatter, and seals a DECISION
`framing chosen: <name>` in the main log with the reason, what was rejected (by
default the other variants with their lenses) and the text hash of the variant
canvas. The variants stay in place as the record. The logic lives in
`hooks/lib/choose.js`, so the session view can call the same function.
`review` does not count that entry as an acceptance.

The guard treats every `canvas.md` and `decisions.md` below the state directory
as research state: a variant canvas takes proposals and refuses `[accepted]`,
and a variant log is written by the harness only. `choose` is refused to the
model under the same name rule as `accept`, behind wrappers and inside inline
programs too.
