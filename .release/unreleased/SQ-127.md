title: The session server carries the explanation, the open checks, the variants and `choose`
bump: minor
plugins:
  - research-harness
---

`POST /api/choose` is the view's copy of `research-harness choose`. It takes
`{name, why, rejected?}` and calls the same `hooks/lib/choose.js` function the
CLI calls, so the two routes write the same bytes: the variant's statements in
`research/canvas.md` and one sealed DECISION in the main log. It stands behind
exactly the checks `/api/accept` has — the session token, the loopback Host, the
Origin when the browser sends one, and the JSON content type after the
single-use code has been traded — and a refusal writes nothing. Choosing while
the main canvas already holds an accepted statement comes back as the library's
`already` code.

`GET /api/state` now lists the project's framings as
`variants: [{name, lens, state}]`, each variant's `state` the same payload the
main canvas is served as, built by one function so the two cannot drift; a
project without variants answers `variants: []`. Every question in the payload
carries `openChecks: [{seq, body}]`, from the same `openChecks` function the
accept path uses to record `**Open at acceptance:**`, so the view and the log
hold one reading of what is still open, never two.

`POST /api/accept` passes `explained` and `rejected` through to
`acceptStatement`, and an empty explanation comes back as the library's
`explanation-required` code with nothing written.
