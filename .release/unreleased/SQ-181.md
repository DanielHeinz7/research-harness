---
ref: SQ-181
title: A second clone joins with the project key
bump: minor
plugins:
  - research-harness
---

`research-harness key export --out <file>.seal.key` writes the project's
sealing key into a file of the holder's choosing, mode 0600, and never prints
it; the file is to be handed over in person, and the command says so. On the
second machine, `research-harness join --key-file <file> --name "<name>"`
checks the key against that clone's log before copying anything, sets the name
and runs `research-harness doctor`. A key that does not verify the log is
refused with nothing copied, and a clone that already holds a different key is
refused rather than overwritten; the same key again is a no-op success.

That closes the trap: `research-harness init` in a clone whose log is already
sealed now refuses to create a second key and points at `join` instead, and a
write without a key on such a log says the same. `research-harness doctor`
gains a check that the key here verifies the log, and notes a missing git
remote and `pull.rebase` set to true — notes, not failures, since a project
with one person and no remote is healthy.
