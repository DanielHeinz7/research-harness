The plugin had no README of its own, and the design document had drifted from
the code in five places over the course of the perimeter work. Both are now
true.

The plugin README covers installing, the three skills, the five CLI commands,
what the guard enforces and what it cannot, the files that belong in Git, and
the one step a co-author runs on a fresh clone: `init` on an existing project
creates the missing sealing key and changes nothing else.

The design document gains the harness state override in its fixed-identifier
table, the `hooks/lib/` layout that shared code actually uses, and the name of
the append path the model records findings through. Three of its claims were
wrong rather than merely stale and are corrected: the `PreToolUse` hook has no
matcher, since SQ-24 made every tool reach the guard; the rule for `canvas.md`
has five clauses, not four; and the claim that the first draft's three
prohibitions "are what clauses 1 and 2 say about one statement at a time" holds
for two of them and is false for the third. A comparison of committed sets
cannot see a proposal promoted to `[stated]`, because it cannot see what a
statement used to be. That sentence had been implemented as written, which
reopened a closed hole with the test suite green; the section now says so, and
why a document that summarises its own completeness is asserting something
testable.

The SQ-16 fragment keeps its original text and gains a note naming the four
tickets that changed the guard after it, so it reads as the history of the rule
rather than as its current statement.

**Outstanding:** the live installation check. Whether Claude Code loads the
plugin from this layout, and whether `$ARGUMENTS` reaches the `!` line of the
`accept` skill, are two assumptions no unit test reaches. Neither has been
confirmed in a running session.
