---
ref: SQ-27
title: The decision log is tamper-evident, and only the harness writes it
bump: minor
plugins:
  - research-harness
---

`research/decisions.md` was append-only, and the guard was faithful to that:
appending was permitted, so the model could append. Nothing bound a `DECISION`
entry to an act by the researcher. SQ-21's D7b and D7c appended a forged
acceptance, once with `Edit` and once with a whole-file `Write`, and the guard
allowed both. D8 showed what that buys. With the forged entry in place, the
unlogged-acceptance count of `canvas-review` dropped from two to the baseline
one: the mechanism whose whole job is to report an acceptance the guard did not
authorise was silenced by a line of Markdown. The guard and its own backstop
failed together.

**Every entry now carries a seal.** The seal is the first sixteen hex of an
HMAC-SHA-256 over the entry's canonical content and the seal of the entry before
it, under a key that `research-harness init` creates once per project under the
harness's own state directory, mode 0600, outside the repository. Chaining makes
the log tamper-evident backwards: altering or removing an entry breaks every
seal after it. The key is what makes an append unforgeable, which a plain hash
chain would not have been, since anyone who can read the log can compute its
next digest. Text hashes are untouched; the two hashes have two jobs.

**The model does not write `decisions.md`.** Every `Edit`, `Write` and
`NotebookEdit` to it is refused, appends included, and the refusal names the
path that replaces them: `research-harness log DISCOVERY|CONSTRAINT <ref>
--body "<text>"`, which seals what it writes and refuses to write a `DECISION`.
The shell rule admits `log` with a literal `DISCOVERY` or `CONSTRAINT`; a
`DECISION`, or a kind the guard cannot read, is refused as `accept` is. `accept`
seals the entry it writes, and refuses before touching the canvas when there
is no key on this machine or the log is already broken.

**Three verdicts, kept apart.** `canvas-review` reports the log as verified,
as unverifiable here (no key on this machine, the normal state of a fresh clone
or a co-author's checkout), or as broken, naming the first entry that fails and
whether its own content, the chain before it, or the unsealed block it anchors
on changed. The harness never repairs a broken log; choosing which version is
true is the researcher's act. An acceptance is logged only by an entry that
verifies. An entry that is legacy, unverifiable here or broken gives no cover,
and the unlogged report says which of those it is, so the reader sees "covered
only by #3, unverifiable here" rather than a bare accusation. D8 re-run against
this release leaves the count at two.

**A log that predates the seal** is not a forgery. Entries without a seal are
legacy: reported once, as unverifiable, never as broken. The first sealed entry
chains onto the SHA-256 of the entire file content before it, so the legacy
block cannot be quietly rewritten either. After the first sealed entry, an
unsealed one is broken; that is the downgrade attack. No ledger is rewritten
and no re-anchoring is needed: `init` on an existing project creates the
missing key and touches nothing else.

**What this costs.** Three narrowings. A statement the researcher accepted
before this release is reported as unlogged until it is accepted again, because
its entry cannot be told from a forged one; the report names the legacy entry
so the researcher knows why. The harness state directory is off-limits to
every tool, reads included: the key is a secret only while the model cannot
`cat` it. And a harness invocation with its own environment on the command line
(`RESEARCH_HARNESS_STATE_DIR=… research-harness log …`) is refused, because it
would seal with a stranger's key and leave the researcher's log reading as
broken at that entry.

**The limit, stated.** The model runs as the same user as the approval path, so
no purely local secret is beyond its reach. What the seal buys is that forging
an entry is no longer writing a line of Markdown: it takes a step into the
harness's own state directory, which the guard sees and denies, and which
leaves the forgery visible as an entry that does not verify if it is not taken.
