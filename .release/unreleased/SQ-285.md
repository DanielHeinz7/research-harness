ref: SQ-285
title: Desktop app: Share resumes after an interruption, commits only the research folder, and keeps logins and key paths out of links and messages
bump: patch
plugins:
  - research-harness
---

In the desktop app, a project counts as shared once its first upload went through: a Share that stopped half-way, or a repository opened with a link it never pushed to, shows Share with co-authors… again, and Share picks it up when the repository is still empty (a repository that holds files is refused as before, and a failed upload puts the old link back). Share, Send and Get updates commit only the research folder, whatever else is staged; the Share dialog now says the project's history goes up as it is. A project folder inside another repository no longer reports that repository's shared copy. A name with control characters, or one git refuses as an author (only signs such as `<>`), is refused with a sentence. Links show without anything in front of the last `@` of the host, for every scheme, and Share and Clone refuse a link that carries a password or token, so it never lands in `.git/config`. A key file this computer cannot read is no key for the sidebar, so Join is offered, and Join sets the unreadable file aside next to itself before it copies the received key; no message names the key's path, and a command-line failure without output reads as a fixed sentence instead of the command line. Clone, Get updates, Send and the Share check stop after 2 minutes without a word from git, but never while the person is typing a login, and say so. Seal chain, log format and guard are unchanged.
