---
ref: SQ-86
title: A loop variable rebound inside the loop is not a loop value
bump: patch
plugins:
  - research-harness
---

SQ-75 taught the guard that `for NAME in W…` over literal words sets NAME to
each of them, so a word using `$NAME` is judged once per value. It dropped
those values only when a statement began with `NAME=`. A body that rebinds the
variable any other way kept them, and in a project without research state
these lines were allowed although bash runs them as `cp a.md research/canvas.md`:

    for f in x y; do f=canvas.md; cp a.md research/$f; done
    for f in x; do export f=canvas.md; cp a.md research/$f; done
    for f in x; do read f < n.txt; cp a.md research/$f; done

`do f=…` starts with `do`, and `export`, `declare`, `read`, `printf -v`,
`mapfile` and `getopts` put the name after the verb, so the leading-assignment
check never saw them. Main denied all three; the SQ-75 candidate allowed them.

The guard now trusts the loop values only if nothing later on the line can
rebind the name. If any word after the `for` header is NAME or starts with
`NAME=` or `NAME+=`, `$NAME` is unknown for the whole line, as it was before
SQ-75. A loop that merely echoes its own name is denied too; that is accepted.

`plugins/research-harness/test/guard-promotion.test.js` gains one SQ-86 test
with the three lines above plus the `printf -v` and `declare` forms as DENY rows
in a bare project. The SQ-75 tests, including the vault loop lines that are
allowed, pass unchanged.
