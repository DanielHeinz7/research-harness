# research-harness — a tour (script draft)

Audience: researchers in IS and management (the paper goes to Organization Science).
Length target: 2:30 to 2:50. Language: English. Voice: Daniel's clone (ElevenLabs, v2).
Embedding: MP4 uploaded by Daniel as a GitHub attachment at the top of the README.
Sources: README.md and plugins/research-harness/README.md at `ac84866` (the rewritten README), plus the appendix note of `46c3f1a`. Anything beyond them is marked `[check]`.
Not claimed: that the guard stops an agent that deliberately goes around it (SQ-209 is open).

Visual material: the session view rendered from fixtures (`dashboard/canvas.html?fixture=…`,
`test/fixtures/view-state-*.json`), terminal output from the recorded walkthrough
(`examples/ai-assistants-interviews/recorded`), and typeset scenes built in HyperFrames.

Built to survive UI changes (Daniel, 2026-10-06):
- The spoken text never names a button, a label, or a layout. It describes what the tool does, so the
  audio stays valid when the UI changes and is recorded only once.
- No hand-made screen recording. UI scenes (5, 8 and the canvas in 2) are captured by a script that opens
  the session view with Playwright from the committed fixtures, at fixed viewport size and fixed points
  in time. Terminal scenes use the real command output from the recorded walkthrough, regenerated by the
  same script.
- Shared state with the accessible-UI lane: `docs/media/showcase-state.json` (proposed 2026-10-06, created
  and kept valid by that lane, built from the public walkthrough). README screenshots and video frames come
  from the same file and the same capture script, so both show the same canvas. Not created yet.
- Typeset scenes (1, 3, 4, 6, 7, 9) are HyperFrames HTML and do not depend on the UI.
- After a UI change: rerun the capture script, then render. Scene lengths come from the audio, so the
  timing does not move.

## 1 · Opening (0:00–0:18)

**Visual:** A blank paper project folder. Agent activity appears around it: three framings, a note, a list of questions. Then one line: *Who decided what?*

> AI agents can now do real work on a paper. They draft framings, write literature notes, and question your argument. The hard part comes later, when a reviewer or a co-author asks which of those parts you actually committed to, and why.

## 2 · The canvas (0:18–0:42)

**Visual:** `research/canvas.md` opens. The nine element headings appear one by one, then three statements with their markers `[proposed]`, `[stated]`, `[accepted]` light up. Lower-third source caption while the canvas is named: *Dorobantu, Gruber, Ravasi & Wellman (2024). The AMJ Management Research Canvas. Academy of Management Journal, 67(5), 1163–1174. doi:10.5465/amj.2024.4005*

> research-harness keeps a paper project in one file, the research canvas. It follows the nine elements of the AMJ Management Research Canvas, from the puzzle to the boundary conditions. Every statement carries a marker. Proposed means an agent suggested it. Stated is something you said. Accepted means you read it and committed to it.

## 3 · Only you accept (0:42–1:08)

**Visual:** Terminal: `research-harness accept 3.1 --explained "…"`, the sentence typed out. A new entry slides into `research/decisions.md` with a seal icon. Then a hand-edited entry shows up red: *does not verify*.

> Agents propose. Only you accept, and only with one sentence of your own about why the statement holds. That acceptance goes into a decision log that only grows. Each entry is sealed with a key kept outside the repository, so a line someone typed into the log by hand does not verify.

## 4 · An honest guardrail (1:08–1:22)

**Visual:** An agent's tool call `accept 3.1` is stopped with a short refusal. Caption: *a guardrail, not a lock*.

> A Claude Code hook refuses the agent's own attempts to accept or to rewrite what you said. It is a guardrail against an agent overstepping, not a lock, and the technical appendix shows where it ends.

## 5 · Compare framings (1:22–1:40)

**Visual:** Session view from `view-state-variants.json`: several framings side by side. One is chosen (`view-state-chosen.json`), the others fade but stay, each with a short reason.

> Parallel agents can write the same study under different lenses. You pick one framing. The others stay in the record, together with your reason for setting them aside.

## 6 · Construct glossary (1:40–1:56)

**Visual:** `research/glossary.md` with one definition. A canvas statement and a manuscript line point to it. The definition changes, and both citing lines turn amber: *stale*.

> Constructs get one definition each, in a glossary. The canvas and the manuscript cite it. When an accepted definition changes, everything that cites it is flagged as stale.

## 7 · Literature notes (1:56–2:14)

**Visual:** A PDF page next to a draft note. Each quotation is matched to the printed page, ticks appear. One quotation does not match, and the note is refused.

> The assistant can draft a literature note from a paper on your disk. The note is refused unless every quotation appears word for word on the page it cites. Paraphrases and numbers are not checked, so you still read the paper.

## 8 · Review, two people, one view (2:14–2:36)

**Visual:** The review output listing open elements, a stale acceptance and an unsourced statement. Then the session view in a browser with two names on the decision history.

> A read-only review lists what is open, what went stale, and which statements have no source. A researcher and a supervisor can share one canvas and go through it in the browser view during a meeting. The log records who wrote each entry.

## 9 · Limits and start (2:36–2:52)

**Visual:** Plain card: what it does not do. Then the two install lines and the repository name.

> It will not tell you whether your research is good. It keeps track of what you decided. To try it, install the plugin in Claude Code and run the canvas on your own paper.
